# 边缘分级推理架构

> 从「P4 能跑 YOLO」到「一套可用的分级架构」
> 本文记录为什么分级、怎么分级、以及实测验证的结果

---

## 一、问题：单点方案都不够好

### 1.1 方案 A：全部放云端

```
传感器 → 云端大模型 → 返回判断
```

| 优点 | 缺点 |
|---|---|
| 算力无限，模型任选 | **延迟 2-3 秒**（实测 1.8-2.5s，峰值 5s+）|
| 无需本地硬件 | **断网即失效** |
| | **图像必须出内网**（隐私问题）|
| | **按月付费**（日均 200 次约 ¥45/月）|

### 1.2 方案 B：全部放本地 MCU

```
传感器 → MCU 上的小模型 → 判断
```

| 优点 | 缺点 |
|---|---|
| 零延迟 | **算力不够**：S3 的 PSRAM 上限 8MB，连 1.5B 纯文本模型都跑不动 |
| 断网可用 | **只能做阈值判断**：无法理解图像语义 |
| 隐私安全 | P4 的 32MB PSRAM 也只够跑 0.5B 以下的极简模型 |

### 1.3 方案 C：全部放本地 PC

```
传感器 → 局域网 → PC 上的 4B 模型 → 判断
```

| 优点 | 缺点 |
|---|---|
| 算力够（4B 多模态）| **延迟 25-30 秒**（模型推理占 20 秒）|
| 隐私安全 | **依赖 PC 常开** |
| 零调用费 | |

---

## 二、结论：必须分级

三个方案都不理想，因为它们在**同一个维度上取舍**——要么快但不会思考，要么会思考但慢。

**分级架构的思路是：不同粒度的事交给不同算力的设备做。**

```
┌──────────────────────────────────────────────────────┐
│  第三级：PC（可选）                                   │
│  · Qwen3.5-4B 多模态模型（INT4，6.6GB）               │
│  · 负责：语义理解、事件描述、长期归档                  │
│  · 延迟：20-30 秒                                     │
│  · 可离线：不影响安全底线                             │
└────────────────────┬─────────────────────────────────┘
                     │ 局域网 HTTP
┌────────────────────▼─────────────────────────────────┐
│  第二级：ESP32-P4（边缘中枢）                         │
│  · YOLO 224×224（567KB 模型）                        │
│  · 负责：目标检测、多传感器融合、本地告警             │
│  · 延迟：70 ms                                        │
│  · 断网可用：✅ 核心功能                             │
└────────────────────┬─────────────────────────────────┘
                     │ WiFi / 串口
┌────────────────────▼─────────────────────────────────┐
│  第一级：感知节点（MCU）                              │
│  · 各类传感器（超声波、红外、温湿度、气体）           │
│  · 负责：数据采集 + 本地阈值自保                     │
│  · 延迟：< 10 ms                                      │
│  · 断网可用：✅ 完全自主                             │
└──────────────────────────────────────────────────────┘
```

## 三、每一级做什么、不做什么

| 层级 | 设备 | 做什么 | **不做什么** | 延迟 |
|---|---|---|---|---|
| L1 | 感知节点 | 采集数据、阈值判断、本地告警 | 不做图像识别、不做跨节点融合 | < 10 ms |
| L2 | ESP32-P4 | 目标检测、多源融合、本地告警、事件上报 | 不做语义理解、不做自然语言输出 | 70 ms |
| L3 | PC | 语义描述、上下文推理、告警文案生成 | 不参与实时安全动作 | 20-30 s |

**核心原则：L3 失效时，L1+L2 必须完整工作。**

## 四、时间线：一次告警发生了什么

```
t = 0 ms      传感器触发（超声波测到距离 < 20cm）
                    ↓
t = 10 ms     L1 节点本地判断：「距离超限」
              → 蜂鸣器立即响（不等任何人）
              → 通过串口/WiFi 上报给 P4
                    ↓
t = 80 ms     L2 (P4) 收到触发，抓图 + 跑 YOLO
              → 「检测到目标，置信度 0.85」
              → 本地声光告警（已响）
              → 组事件 JSON，准备上报 PC
                    ↓
t = 100 ms    L2 → L3 异步发送事件（不等返回）
                    ↓
t = 1.5 s     PC 收到图像
                    ↓
t = 25 s      PC 返回语义描述：「画面中有一名人员
              在危险品区附近停留，建议核实」
              → 语音播报
              → 微信推送
```

**关键点：用户在 10ms 内就听到蜂鸣器，25 秒的语义描述只是增强信息。**

### 4.1 这个时间线是怎么验证的

| 环节 | 数据来源 |
|---|---|
| L1 阈值判断 < 10ms | 理论值（纯 GPIO 读取 + 比较） |
| **L2 YOLO 70ms** | **实测**（30 次连续推理，抖动 0.1ms）|
| 抓图 1.5s | 实测（ESP32-CAM HTTP `/capture` 平均 285ms + 传输）|
| L3 25s | 实测（PC 上 Qwen3.5-4B 推理）|

**只有 L2 的 70ms 是本次新增的实测数据，但它是整个架构成立的关键。**

在此之前，「边缘能实时做视觉判断」只是假设；现在是实测 14.3 FPS。

## 五、降级矩阵

分级架构的价值在于**每一级失效时，其他级能顶上**。

| 失效情况 | L1 | L2 | L3 | 系统表现 |
|---|---|---|---|---|
| 正常 | ✅ | ✅ | ✅ | 全功能 |
| **PC 关机/断网** | ✅ | ✅ | ❌ | 本地告警正常，无语义描述与推送 |
| **P4 离线** | ✅ | ❌ | — | 节点自主阈值告警，无视觉确认 |
| **单个节点离线** | 部分 | ✅ | ✅ | 该区域无数据，标记为降级 |
| **摄像头失效** | ✅ | 部分 | ✅ | 无视觉，只能靠传感器 |
| **C6 协处理器异常** | ✅ | ✅ | — | 无网络，P4 本地判断仍工作 |
| **P4 掉电** | ✅ | ❌ | — | **最小可用**：节点本地告警 |

### 5.1 最重要的一行

> **P4 掉电时，节点仍然能本地告警。**

这是架构的安全底线：任何中间层失效，最基层的告警不受影响。

实现方式：**每个节点的阈值判断在自己身上跑，不等任何人批准**。

```c
// 节点固件里
if (distance < THRESHOLD_DANGER) {
    gpio_set_level(BUZZER_PIN, 1);    // 立即响，不等上位机
    report_to_hub();                   // 上报是"通知"，不是"请示"
}
```

## 六、为什么是「70ms」这个数字重要

| 方案 | 单次判断延迟 | 相对倍数 |
|---|---|---|
| PC 跑 Qwen3.5-4B | 25-30 秒 | 基准 |
| 云端 API | 1.8-2.5 秒 | 快 10 倍 |
| **P4 跑 YOLO** | **70 毫秒** | **快 357-428 倍** |

**从「秒级」进入「毫秒级」，是质变不是量变：**

- 秒级：只能做事后取证（事情已经发生了）
- 毫秒级：可以做事前干预（在事情发生前响应）

比如：

| 场景 | 秒级方案 | 毫秒级方案 |
|---|---|---|
| 人员闯入 | 25 秒后知道有人进来（人已经走远） | 70ms 内声光警告（人还在门口） |
| 货架倾倒 | 25 秒后拍到了 | 70ms 内检测到并通知 |
| 小车避障 | 无法做（来不及） | 70ms 内刹车 |

**这就是为什么必须在边缘做视觉，而不是全放 PC。**

## 七、硬件选型依据

### 7.1 为什么 P4 而不是 S3

| 项目 | ESP32-S3 | ESP32-P4 | 结论 |
|---|---|---|---|
| PSRAM | 最大 8MB | **32MB** | P4 能装下 YOLO + 帧缓冲 |
| 摄像头接口 | DVP（并口） | **MIPI-CSI** | P4 带宽高得多 |
| AI 加速 | 向量指令 | **AI 指令扩展** | P4 更快 |
| WiFi | **内置** | ❌ 需外挂 C6 | S3 占优 |
| 价格 | 约 ¥13 | 约 ¥85 | S3 便宜 |

**结论**：如果只是做传感器采集，S3 够用且更便宜；
如果要跑视觉模型，必须 P4。

### 7.2 P4 的 32MB PSRAM 够不够

实测：

```
模型占用   : 1.66 MB
PSRAM 总量 : 32 MB
剩余       : 30.34 MB
```

**结论：绰绰有余。**

即使换成更大的模型（比如 5MB），也还有 27MB 可用。

### 7.3 为什么 P4 不能跑 LLM

| 项目 | 需求 | P4 能力 | 差距 |
|---|---|---|---|
| 4B 模型（INT4） | 约 6.6 GB | 32 MB | **200 倍** |
| 1.5B 模型（INT4） | 约 1 GB | 32 MB | **31 倍** |
| 0.5B 模型（INT4） | 约 300 MB | 32 MB | **9 倍** |

**即使最小的可用 LLM 也装不下。**

就算装下了，P4 的算力（400MHz 双核 RISC-V，无矩阵加速）也算不动——
实测 YOLO 的 224×224 输入就要 70ms，一个 1.5B 模型单次前向至少几十秒。

**所以：P4 做视觉（YOLO 这类小模型），LLM 交给 PC。**

## 八、如果要从头再做一次

### 8.1 会被改进的地方

| 当前问题 | 改进方向 |
|---|---|
| 只有猫的模型，不能识人 | 训练人形 + 货架 + 烟雾数据集 |
| 70ms 里含 19ms 缩放 | 让摄像头直接输出 224×224 |
| C6 固件 0.0.0 | 升级到新版，启用 SDIO 聚合 |
| PC 必须常开 | 换成树莓派 5（¥600，可 24 小时运行）|
| 无 BLE | 升级 C6 固件后可支持 |

### 8.2 不会改变的地方

| 决策 | 理由 |
|---|---|
| **P4 做边缘视觉** | 32MB PSRAM + MIPI-CSI 是最优组合 |
| **PC/算力板做语义** | 4B 模型需要 6.6GB，只有这个层级能承载 |
| **分级而不是单点** | 单点方案必然在「快」和「聪明」之间二选一 |
| **本地而非云端** | 隐私 + 断网 + 零费用，三个都是硬需求 |

---

## 九、一句话总结

> **分级不是为了炫技，是因为没有单一设备能同时满足「快、聪明、便宜、离线」四个要求。**
> **把合适的任务放到合适的层级，用 70ms 的确定性兜住安全的底，用 25 秒的智能做增值。**
